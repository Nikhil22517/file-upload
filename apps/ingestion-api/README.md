# Ingestion API (TypeScript · Hono · Drizzle · Postgres)

Upload client report files. Each workspace sets up its own report templates (there are no built-in reports); an
upload is matched to one, checked (duplicate, foreign DSP, missing period), then its rows are saved in `report_row`
and the template's analytics in `report_metric`. Driver identities and KPIs come later.
Design: [`Ingestion_and_Attribution_Design.md`](../../Ingestion_and_Attribution_Design.md).

| Concern | Choice |
|---|---|
| HTTP | Hono on Node 22 |
| Postgres | Drizzle ORM; migrations generated by drizzle-kit (`packages/db/drizzle`) |
| CSV / XLSX / PDF | papaparse / exceljs / pdfjs-dist |

The logic is split the monorepo way; this API and the web app (`apps/web`) run the same service code:

```
packages/ingestion           @platform/ingestion           read files, PDF readers, templates, analytics (no database)
packages/db                  @platform/db                  Drizzle schema + migrations, Postgres pool
packages/ingestion-service   @platform/ingestion-service   upload, confirm, teach, import, list: plain functions over the two above
apps/ingestion-api           @platform/ingestion-api       HTTP routes over the service (Postman, other systems, uploads by URL)
apps/web                     @platform/web                 TanStack Start screens; server functions over the service
```

## Run

```powershell
pnpm install                                # from the repo root

cd apps/ingestion-api
# Option A: Postgres in Docker, API on your machine
docker compose up -d                        # Postgres :5432
copy .env.example .env
pnpm dev                                    # http://localhost:8000

# Option B: everything in Docker (builds from the repo root)
docker compose --profile app up -d --build
```

Try it with the sample reports (sub-folder names map to workspaces, see the script):

```powershell
pnpm upload-folder "C:\Users\NikhilSharma\Downloads\DSP Reports"
```

Or click through it in Postman: import `postman/ingestion-api.postman_collection.json` and run the folders in order
(each request saves the ids the next one needs), or run it in the terminal with `pnpm postman` (API must be running).

Tests need Postgres from `docker compose up -d`:

```powershell
pnpm test
```

Changing the Postgres schema: edit `packages/db/src/schema.ts`, then `pnpm --filter @platform/db db:generate`.
Migrations run automatically at startup.

Stop: `docker compose --profile app down` (add `-v` to delete the data volumes).

## API

| Method | Path | What it does |
|---|---|---|
| POST | `/workspaces` | Create a client workspace (`code` = DSP code, used by the foreign-DSP check). It starts with no templates |
| GET | `/workspaces` | List workspaces |
| POST | `/workspaces/{ws}/files` | Upload 1–25 files: multipart `files`, or JSON `{"files": [{"url": "...", "file_name"?: "..."}]}` for files you stored yourself. Optional `reference_date` (daily reports) and `reference_week` (`2026-W27`, weekly reports). Each is matched to a template, then imported or held; an unknown report comes back with its `draft` template |
| POST | `/workspaces/{ws}/files/{id}/confirm` | Resolve a held file: `accept_warnings`, `reference_date` or `reference_week` |
| GET | `/workspaces/{ws}/files` · `/files/{id}` | Upload history (optional `?stage=`), one file (with `rowCount`, `issueCount`, `headerRow`) |
| GET | `/workspaces/{ws}/files/{id}/rows` | The file's saved rows (`limit`, `offset`, `with_issues=true`) |
| GET | `/workspaces/{ws}/files/{id}/metrics` | The file's analytics, as its template defines them |
| POST | `/workspaces/{ws}/files/{id}/reimport` | Read an imported or failed file again (replaces its rows and analytics) |
| GET | `/workspaces/{ws}/files/{id}/template-draft` | For an unknown upload: guessed name, header row, column types and roles, period kind, PDF reader and its sections, sample values (`?header_row=` to redraft) |
| POST | `/workspaces/{ws}/templates` | Teach a report from an upload at `needs_template`. `{"file_id": "..."}` accepts the draft; add any of the controls below to change it. Other waiting uploads of the same report are imported too |
| GET | `/workspaces/{ws}/templates` · `/templates/{id}` | The workspace's templates (with their upload counts) |
| PATCH | `/workspaces/{ws}/templates/{id}` | Change a template's controls (below). Analytics are recomputed for every upload at once |
| GET | `/workspaces/{ws}/reports/daily` · `/reports/weekly` | Daily (or weekly) reports by period: every such report with the dates (weeks) it has data for, and one report's rows and analytics for one day (week). `?template=` and `?period=` (`2026-07-01` / `2026-W27`); defaults: the report with the newest data, at its latest period. When several uploads cover a period, the latest per station is shown |
| GET | `/workspaces/{ws}/templates/{id}/metrics` | The template's analytics across its uploads (`?metric=` for one) |

## Templates: what the workspace controls

There are no built-in report types. A new workspace knows no reports; its users set up each one once, from its first
upload (a draft the system guesses), and can change it at any time. A template holds:

| Control | Field | What it does |
|---|---|---|
| Name | `name` | How the report is called everywhere |
| Columns | `columns: [{ key, type?, role?, include? }]` | Each column's type (`text`, `id`, `int`, `decimal`, `percent`, `date`, `datetime`, `week`, `yn`), its role (`driver_id`, `driver_name`, `date`, `week`) and whether to keep it (`include: false` skips it). Send only the columns you change |
| Period | `period_kind: 'day' \| 'week'` | What one upload covers. When neither its columns nor its file name say, the uploader gives a date (daily) or an Amazon week (weekly) |
| PDF sections | `sections: string[] \| null` | Which parts of a PDF to keep, e.g. `Driver` rows and/or the `Summary` values; `null` = all |
| Analytics | `metrics: [{ name, op, column, by, where? }]` | Numbers computed from each upload's rows: `op` = `sum`, `avg`, `min`, `max`, `count`, `count_distinct`; `by` = `file`, `driver`, `day`, `week`; `where` = `{ column, equals }` to use only some rows. Stored in `report_metric` |

Column, section and period changes apply to the uploads that follow (re-import an upload whose original was kept to
apply them to it). Analytics are recomputed from the saved rows, so changing them never needs the originals.

## Recognising reports

1. A template of this workspace whose columns match the file's header row (any column order). The header is looked
   for in the template's row first, then in the first 15 rows, so a preamble that grows or shrinks still matches.
2. The file name breaks ties between templates with the same columns. Its fixed part is the pattern, and what
   changes per upload is replaced and kept as data:
   `Quality_Overview_PTLG_DNJ4_2026-07-01 (1).csv` → `quality_overview_{dsp}_{station}_{date}`.
   The date or week in the name is used as the report's period when the columns have none.
3. Mostly the same columns → `needs_confirmation` with `template_changed`; confirming updates the template.
4. Otherwise `needs_template`: the user sets up the report once, and later uploads go straight through.

## PDFs

A PDF becomes a table through a **reader** for its layout (`packages/ingestion/src/pdf-readers.ts`), then goes through
the same template steps as a CSV. Readers so far: the **Amazon DSP Scorecard** (each driver's metrics, plus the
scorecard's own values: overall standing, every metric with its value and tier, the compliance statuses) and **Amazon
POD Details** (each driver's photo counts, plus the POD summary and the rejects breakdown). Each table has a `Section`
column (`Driver`, `Summary`...), which templates choose from. A PDF no reader knows is stored as a file only
(`stored_file_only`); adding a reader for its layout makes it importable.

## File stages

`queued` → `imported` (rows in `report_row`, analytics in `report_metric`) | `stored_file_only` (a PDF no reader knows) |
`failed` (`error` says why). A file is imported as soon as it passes the checks.
Held for a person, in this order: `needs_confirmation` (duplicate, foreign DSP, changed columns),
`needs_template` (a report this workspace hasn't set up), `needs_reference_date` (no date or week for its period).
In the upload response only: `rejected` (too large, unreadable, or its URL could not be downloaded; nothing is stored).

## Where the originals live

- **Sent by URL:** they stay where you put them; the API downloads them and keeps no copy. The URL must stay readable
  until the file is imported (a held file is downloaded again when it is confirmed or taught), so give long-lived links.
  `FILE_URL_HOSTS` (comma-separated) limits which hosts the API will download from; set it to your bucket's host.
- **Uploaded as files:** kept in `STORAGE_DIR` only until the rows are imported, then deleted.
  PDFs without a reader and failed imports keep theirs. `KEEP_FILES=true` keeps every original (needed for `reimport`).
